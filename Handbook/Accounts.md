# Accounts

This page contains a list of accounts *primarily maintained by the Data Department*. First-party accounts (O365, iasWorld, etc.) are excluded.

**Shared accounts** have one user whose credentials are shared among multiple team members. **Individual accounts** are tied to an individual team member. In general, only Director-level staff members should have access to shared accounts.

When **sharing credentials for a shared account** with a Director-level staff member, make sure to share the credentials over a secure communication channel. Common ways of sharing these credentials include writing them on a sheet of paper that you share in person and shred after use, or using the secure sharing feature of a major password manager.

## AWS Service Accounts

We maintain a few service accounts in AWS IAM to allow automated jobs to access the AWS resources they need.

There are two different types of IAM resources that we use to manage service accounts in AWS:

1. ⏱️ **IAM roles**: Our preferred approach for services is to run them in GitHub Actions and configure them to request temporary authentication tokens for a dedicated IAM role using OIDC. In these cases, each service gets its own IAM role with the minimal permissions required to run the service, and then we configure a trust relationship on the IAM role to allow the repo that hosts the workflow to assume the role using OIDC. We also set maximum session durations for each role so that its temporary credentials are only valid for the length of time that the job takes to run in a GitHub workflow.
2. 👤 **IAM users** (deprecated): We use long-lived API credentials for IAM users to authenticate some legacy services that can't run on GitHub Actions and need to run on a different platform like our Ubuntu server, our Windows VM, or Tableau. In these cases, we create the IAM user without console access, we give the user the minimal permissions it needs to run the service, and then we store long-lived API credentials on the platform that runs the service.

### Monthly AWS Account Review

Every month, a senior staff member on our team should review our AWS IAM roles and users to ensure proper access.

1. Review our [IAM user list](https://us-east-1.console.aws.amazon.com/iam/home?region=us-east-1#/users).
  1. Ensure that you recognize every user account. If there are any user accounts you don't recognize, check with the CCAO Data Team, CCAO IT, and our AWS vendor to see if anyone is using that user account. If no one is using the user account, delete it immediately and inform CCAO IT.
  2. Review any users whose last activity was more than 30 days ago. Check with the owners of those users to see if they still need access, or if instead you can delete the user.
2. Review our [IAM role list](https://us-east-1.console.aws.amazon.com/iam/home?region=us-east-1#/roles).
  1. Ignore any roles that start with `AWS` or `Amazon`, since these are managed roles. You can also ignore any roles that our AWS vendor uses.
  2. Compare our roles against the list of [known service accounts](#aws-service-accounts). If there are any roles that you don't recognize, check with the CCAO Data Team, CCAO IT, and our AWS vendor to see if anyone can account for the role. If no one can account for the role, delete it immediately and inform CCAO IT.
  3. Review any roles whose last activity was more than 30 days ago. Check with the owner of the service that uses that role to see if it's still necessary, and delete any deprecated roles.
